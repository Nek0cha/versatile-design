# 設計書：web の動き・WebGL・フォント・技術スタックの拡充

- 作成日：2026-10-06
- 状態：設計の承認済み、実装計画の作成前
- 対象：`design-core` と `web`（主にサイト系）

## 1. 目的

`web` のサイト系で生成されるページを、次の4点で拡充する。

1. GSAP の演出の型を増やし、Three.js による WebGL の演出を新しく扱えるようにする。
2. フォントの配信元を Google Fonts の外に広げ、定番の書体に偏る組版から離れる。
3. 作る前に、コンセプトの案と技術スタックを利用者に提案して選んでもらう流れにする。
4. 参考サイトを 5〜15 件追加して計測し、1〜3 の数値と原則の根拠にする。

### 1.1 成功の基準

- サイト系の新規の依頼で、コンセプトの案 2〜3 個と技術スタックの提案が1回のメッセージで出る。「おまかせ」の指示があれば質問せずに進む。
- 記憶のフックに動きや 3D を選んだ案では、`motion-web.md` と `webgl.md` の型に沿った実装が出る。動きを減らす設定、WebGL が使えない環境、画面外での停止、片付けへの対応が欠けない。
- 書体の組の表に、Google Fonts 以外の配信元の組が含まれ、それを選んだ場合に読み込みのコードまで正しく出る。
- `npm run check:skills`（禁止語のファイルを指定した状態を含む）、`npm run check:recipes`、`npm test` がすべて通る。

### 1.2 前提

- 利用者は基本的にスキル作者本人である。
- 依存は最小限にする。Three.js は `three` だけを使い、React Three Fiber と drei は使わない。
- 実例の取り扱いは `README.md` の「実例の取り扱い方針」に従う。参考サイトの名前とドメインは、設計書・計画書・スキルのファイル・コミットメッセージのどこにも書かない。

## 3. 作る前の確認の流れ

対象のファイル：`skills/design-core/references/concept-brief.md`、`skills/design-core/SKILL.md`、`skills/web/SKILL.md` の手順2。

現在の決まり「宣言したら確認を待たずに進める」を、次の表に置き換える。

| 状況 | コンセプト | 技術スタック |
|---|---|---|
| 新規・サイト系 | 案を 2〜3 個出して選んでもらう | 提案して確認する（コンセプトの案と同じメッセージで出す） |
| 新規・アプリ系 | 今までどおり宣言して進める | 提案して確認する |
| 既存のプロジェクト・サイト系 | 案を 2〜3 個出して選んでもらう | 既存のものに合わせ、質問しない |
| 既存のプロジェクト・アプリ系 | 今までどおり宣言して進める | 既存のものに合わせ、質問しない |
| プロンプトに「おまかせ」「確認なしで」などがある | 最も良い案を自分で選び、選んだ理由を添えて宣言して進める | 4節の表から自分で選び、理由を添えて宣言して進める |

- 新規・既存の判定は、作業ディレクトリに `package.json` があるかどうかで行う。
- 質問したら、回答があるまで実装に進まない。
- 1つの案には、誰に、どんな印象を、記憶のフック、動きの強さ（静か／GSAP の演出あり／Three.js あり）、書体の組の記号、テーマを書く。
- 案同士は記憶のフックの種類を変える（例：巨大な文字、写真の配置、WebGL の面）。形容詞だけが違う案を並べない。
- 動きの強さは記憶のフックから決める。フックが動きや 3D そのものである案だけを「GSAP の演出あり」「Three.js あり」にする。
- `concept-brief.md` の5節に、案を出すときの書式を足す。宣言の書式は「おまかせ」とアプリ系のために残す。

## 4. 技術スタックの決め方

新しく `skills/web/references/stack.md` を作る。手順2で読む。

| 規模・性質 | 提案するもの |
|---|---|
| 1〜数ページの LP、ポートフォリオ | React ＋ Vite |
| ページが多い、ブログやお知らせなど内容が中心のサイト | Astro（動く部分だけ React の島にする） |
| ログイン、データの読み書きがあるアプリ | React Router（フレームワークモード）または Next.js |

- 提案には、選んだ理由を1文で添え、次点を1つ併記する。
- どれを選んでも、Tailwind CSS v4、React Aria Components、Iconify、トークンの定義は共通とする。
- フレームワークごとに違う点を表にまとめる：最初の CSS の置き場所、`"use client"` の要否、フォントの読み込み方、ファビコンの置き場所（`references/favicon.md` と整合させる）、GSAP と Three.js をクライアントだけで動かす方法（Astro の `client:visible` など）。
- `web` の手順4の「React と Tailwind CSS v4 の最小構成を用意し」を、「`stack.md` で決めた構成を用意し」に書き換える。
- `README.md` の「必要なもの」に、生成物のフレームワークが選ばれることを書く。

## 5. 参考サイトの追加

### 5.1 選び方

- 候補はスキル作者の指定（1件）と、Web 検索で集めた候補から、スキル作者が選ぶ。合計 5〜15 件にする。
- 検索では、GSAP や Three.js を使っているサイト、Google Fonts 以外の書体を使っているサイトを優先する。ポートフォリオ、ブランドサイト、事業サイトが偏らないようにする。
- 候補の一覧（名前と URL）はスクラッチ領域の `reference-map.md` に書き、リポジトリに含めない。

### 5.2 計測

既存の観察の方法（`observations/site.md` の「観察の方法」）に次の項目を足す。

- WebGL：canvas の数と大きさ、`three` の読み込みの有無、演出の種類（背景の面、画像のゆがみ、粒子、3D の物体）、スクロールとのつなぎ方。
- GSAP：使っているプラグイン、ピン留めの有無、横スクロールの有無、`scrub` の値。
- フォント：書体名と配信元（Google Fonts、Fontshare、自前配信、有料の配信サービス）。
- 動きを減らす設定と WebGL が使えない場合の代わりの表示の有無。

計測には Playwright を使い、計測用のスクリプトはスクラッチ領域に置く（リポジトリに含めない）。

### 5.3 記録

- `observations/site.md` に「サイト5」以降の匿名ラベルで追記し、「共通する傾向」の表と箇条を全件で作り直す。
- 珍しい有料フォントは名前を書かず、「コントラストの強い有料のセリフ体」のような分類で書く。無料で配信されているフォントと OFL のフォントは名前を書いてよい。
- 1つのサイトの数値の組をまとめて `mode-site.md` に移さない。傾向として複数のサイトから取り出す。
- 計測後、`mode-site.md` の調整欄と `motion-web.md` の調整欄の数値を、新しい傾向に合わせて見直す。
- 禁止語のファイルに追加したサイトの名前とドメインを足し、`REFERENCE_DENYLIST` を指定して `npm run check:skills` を通す。コミットの前に `git log --all -p` に対しても同じ禁止語で検索する。

## 6. 動き

### 6.1 GSAP（`motion-web.md` の4節に追加）

候補は次の5つとし、5節の観察で使われていたものを優先して入れる。観察で1件も見られなかった型は入れない。

- ピン留め＋横スクロール
- Flip（レイアウトの切り替え）
- 画像の切り抜き（`clip-path`）での登場
- スクロールの速さに反応する帯
- ページの読み込みの演出

各型に、使う場面、使わない場面、コード例、動きを減らす設定のときの組み立てを書く。所要時間とイージングは調整欄とトークンの範囲に収める。

### 6.2 Three.js（新しく `skills/web/references/webgl.md` を作る）

`three` だけを使い、React の `useEffect` の中でレンダラー、シーン、カメラを作り、戻り値の関数で片付ける形を基本の型にする。

入れる型：

- 見出しや画像の裏に置くシェーダーの面
- 画像のゆがみと切り替え
- 粒子と線
- スクロールと uniform を GSAP でつなぐ書き方（`gsap.to(uniforms.uProgress, { value: 1, scrollTrigger: … })`）

必ず守る決まり：

- 動きを減らす設定のときは、1フレームだけ描いて止める。
- WebGL が使えない環境では、同じ位置に静止画か CSS の背景を出す。
- `IntersectionObserver` で画面外に出たら描画のループを止める。
- 片付けで、ジオメトリ、マテリアル、テクスチャ、レンダラーを `dispose()` する。
- `renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2))` とする。
- canvas は装飾として `aria-hidden="true"` にし、伝えたい内容は HTML の文字で置く。

`web` の `SKILL.md` の手順4に、記憶のフックが WebGL の場合だけ `webgl.md` を読む指示を足す。`motion-web.md` の1節の「ライブラリの使い分け」の表に Three.js の行を足す。

### 6.3 禁止事項

`../design-core/references/anti-patterns.md` に、記憶のフックと結び付かない定番の WebGL の演出（揺れ続ける球体、マウスに付いてくる粒子、画面全体の虹色のグラデーションの面）を足す。番号は既存の続きとする。機械で判定できる項目（WebGL を使っているのに動きを減らす設定への対応がない、など）は `lint-rules.mjs` にルールとして足すかを実装計画で判断する。

## 7. フォント

対象のファイル：`skills/design-core/references/typography-ja.md`。

- 配信元を Google Fonts、Fontshare、OFL のフォントの自前配信の3つに広げる。有料フォントは載せない。
- 組み合わせ表に「配信元」の列を足す。主役にしない書体の決まりは今のまま残す。
- 2.2 節「読み込み」を配信元ごとに書き分ける。自前配信では、フォントファイルを生成するプロジェクトの `public/fonts/` などに置き、`@font-face` を書き、ライセンスの文書を同じ場所に置く。
- 調整欄の「組み合わせを追加するときの手順」の手順3を、配信元ごとの確かめ方に書き換える。Fontshare は配信の URL が 200 を返すこと、OFL のフォントは配布元でライセンスが OFL であることとウェイトの有無を確かめる。
- 5節の観察で使われていた書体の傾向（分類、太さ、字間）を、組の選定の根拠にする。
- 各印象の節に、Google Fonts 以外の配信元の組を少なくとも1つ入れる。

## 8. 検証

- `tools/check-recipes.mjs` の対象を、`references/components/` に加えて `references/motion-web.md` と `references/webgl.md` に広げる。
- 型検査のために、開発用の依存に `three`、`@types/three`、`gsap`、`@gsap/react`、`lenis` を足す（ロックファイルに合わせて npm を使う）。
- `npm test`、`npm run check:recipes`、`npm run check:skills` を通す。
- 実際の生成で確かめる：新規のサイト系の依頼を1つ与え、案と技術スタックの提案が出ること、Three.js の案を選んだ場合に 6.2 の決まりがすべて満たされること、PC 幅とスマートフォン幅のスクリーンショットで WebGL の面が描かれていることを確かめる。

## 9. 進め方

1. 参考サイトの選定と計測（5節）。スキル作者が候補を選ぶ時点で一度止まる。
2. 作る前の確認の流れと技術スタック（3節、4節）。1 と並行して進められる。
3. 動き（6節）とフォント（7節）。1 の観察結果を使う。
4. 検証（8節）。

実装計画は 1〜4 をまとめて1本で作り、各段階の終わりでコミットする。
