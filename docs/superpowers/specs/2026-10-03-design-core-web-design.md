# 設計書：汎用デザインスキル（design-core ＋ web）

- 作成日：2026-10-03
- 状態：レビュー待ち
- 対象サブプロジェクト：第1弾（`design-core` と `web`）

## 1. 目的

Claude のスキル（SKILL.md 形式）として、プロ水準で「AI感のない」デザインを出力させる仕組みを作る。

スキルはモデルの地力を上げるものではなく、スキル作者の審美眼を言語化・数値化してモデルに渡すための器である。抽象的な指示（「センスよく」など）は効かず、放置すると出力は平均的で無難なデザインに寄る。この「平均への回帰」を、具体的な禁止事項・数値・手順・機械的な検査で防ぐことを狙う。

### 1.1 成功の基準

- 同じお題をスキルなし／スキルありで生成したとき、スキル作者がスクリーンショットを見比べて、スキルありの方が明らかにAI感が薄いと判断できる。
- スキルありの出力で、自動チェック（`lint-design.mjs`）の違反がゼロになる。

### 1.2 前提

- 利用者は基本的にスキル作者本人である。友人に配布する可能性がある。
- 好みは全開で作る（中立化しない）。ただし、他の利用者が自分の好みで上書きできる仕組みを持たせる（6章）。
- Web の生成物は React 前提とする。Tailwind CSS（v4）も前提に含める。
- 生成する UI の言語は日本語が中心で、英語が混ざる。
- このスキルは frontend-design スキルと併用しない前提で作る。

## 2. 全体の分割と今回の範囲

媒体ごとにスキルを分け、共通の思想を `design-core` に置く。

| スキル | 役割 | 今回 |
|---|---|---|
| `design-core` | 媒体に依存しない思想、コンセプト先行の手順、禁止リスト、色と文字の原則 | 作る |
| `web` | Web のサイト系・アプリ系。React ＋ Tailwind ＋ React Aria Components | 作る |
| `poster` | ポスターなどの静的なグラフィック | 将来 |
| `motion` | 動画（モーショングラフィックス） | 将来 |
| `copywriting` | AIっぽくない文章（キャッチコピー、本文）の生成 | 将来 |

今回やらないこと：`poster`、`motion`、`copywriting`、友人向けの配布パッケージ化。

`copywriting` ができるまでの暫定ルールとして、生成物内の仮の文章はダミーであることが分かる形で置く（例：「ここに見出し」）。「Unlock the power of〜」のような定型コピーを生成しない。

### 3.1 スキル間のつながり

- `web/SKILL.md` の冒頭で、`design-core/SKILL.md` と `design-core/user-preferences.md` を読むよう指示する。
- `references/` は毎回すべてを読ませず、手順の中で必要になった時点で必要なファイルだけを読ませる。文脈の消費を抑え、重要な指示が埋もれるのを防ぐためである。

## 4. 各要素の設計

### 4.1 作業の流れ（`web/SKILL.md`）

1. **読み込み**：`design-core/SKILL.md` と `user-preferences.md` を読む。
2. **コンセプトを決める**（コードを書く前に必ず行う）
   - 次の3行を書き出し、ユーザーに宣言する。
     - 誰に：使う人、見る人
     - どんな印象を：形容詞2〜3個
     - 何で記憶に残すか：記憶のフックを1つ
   - サイト系かアプリ系かを判定する（4.2節）。
   - テーマを決める（4.3節）。
   - 確認のために止まらず、宣言してそのまま進める。依頼が曖昧で判断できない場合に限り質問する。
3. **トークンを決める**：色、和文と欧文の組み合わせ、余白の段階、角丸、影、イージングを最初に `@theme` に定義する。部品はすべてトークンから作る。
4. **実装する**：部品は `components/` のレシピを、アニメーションは `motion-web.md` を参照する。
5. **検証する**
   - `lint-design.mjs` を実行し、違反がゼロになるまで修正する。
   - `screenshot.mjs` で PC 幅とスマートフォン幅、対応する全テーマのスクリーンショットを撮る。
   - `critique.md` の項目で自己批評し、修正する。自己批評の周回は最大2周とする。それ以上の周回は無難な方向への収束を招きやすいためである。
6. **報告する**：決めたコンセプト、実施した検証、直しきれなかった点を報告する。

### 4.2 サイト系とアプリ系の判定

サイト系とアプリ系は「良いデザイン」の基準がほぼ逆であるため、1つの `web` スキルの中でモードを判定し、読み込む資料を切り替える。

| | サイト系 | アプリ系 |
|---|---|---|
| 例 | ポートフォリオ、企業サイト、LP | ダッシュボード、ツール、設定画面 |
| 目的 | 記憶に残る、世界観を伝える | 迷わず操作できる、毎日使っても疲れない |
| 見せ場 | 大胆なタイポグラフィ、余白、スクロール演出 | 部品の作り込み、状態の伝え方、情報の密度 |
| 読む資料 | `mode-site.md`、`observations/site.md` | `mode-app.md`、`intuitive-ui.md`、`observations/app.md` |

両方の性質を持つ依頼（例：アプリの紹介 LP と管理画面の両方）は、画面ごとにモードを判定する。

### 4.3 テーマ

- 既定は「ダークを基本にし、ライトにも対応する」。
- プロンプトに「ダークのみ」「ライト基本」「ライトのみ」などの指定があれば、それに従う。
- どの場合も色はトークンで定義し、テーマごとに値を差し替えられる構造にする。

### 4.4 部品のレシピ（`web/references/components/`）

各ファイルに、守るべき原則と React Aria Components ＋ Tailwind（自前トークン）による短いコード例を記載する。

| ファイル | 主な内容 |
|---|---|
| `button.md` | 主要／副次／危険な操作の区別、押下時の反応、ロード中の状態 |
| `text-input.md` | テキスト入力とテキストエリア、ラベルとエラーの位置 |
| `number-field.md` | 自前の増減ボタン（ブラウザ標準の矢印は消す）、長押しによる連続増減、単位表示、等幅数字、スライダーとの組み合わせ、リセット |
| `select.md` | 開閉の動き、選択中の印、キーボード操作、長いリストでの検索欄 |
| `checkbox-radio-switch.md` | チェックボックス、ラジオ、スイッチの状態表現 |
| `tabs.md` | 選択中の表現、切り替えの動き |
| `modal.md` | ダイアログの閉じ方、背景のスクロール固定、フォーカスの扱い |
| `toast.md` | 表示位置、自動で消える時間、元に戻す操作 |
| `tooltip-popover-menu.md` | ツールチップ、ポップオーバー、メニューの使い分け |
| `scrollbar.md` | 細く、トークンの色で、ホバー時のみ濃くする。OS ごとの差の吸収 |
| `loading.md` | スケルトン、進捗表示。0.3秒未満の処理では何も表示しない。スピナー単独で済ませない |
| `states.md` | 空状態、エラー、フォーカスリング、無効状態、ホバー時のみ現れる操作 |
| `selection.md` | `user-select` のルール（4.5節）、コピーボタンを置く場所 |
| `icons.md` | Iconify の使い方、アニメーション付き SVG、アイコンとラベルを組にするルール |

部品の土台は React Aria Components とする。理由は、見た目を一切持たないため既製 UI ライブラリの見た目が入り込まないこと、数値入力などの複雑な部品が操作性まで含めて揃っていること、アクセシビリティが堅いことである。shadcn/ui の既定の見た目は使わない。

### 4.5 `user-select` のルール

- `none` にするもの：ボタン、タブ、ナビゲーション、メニュー項目、アイコン、バッジ、チェックボックスやトグルのラベル、ドラッグできる要素。
- 選択可能なまま残すもの：本文、見出し、記事の中身、エラーメッセージ、ID・注文番号・API キー・コード・メールアドレス、入力欄の中身。
- コピーされやすい値の横にはコピーボタンを置く。

### 4.6 Tailwind の扱い（`tokens-tailwind.md`）

Tailwind の初期値（標準パレット、`rounded-*`、`shadow-*` の既定値）は AI 感の発生源であるため、次のように縛る。

- 色、角丸、影、フォント、イージングは、すべて Tailwind v4 の `@theme` で自前のトークンとして定義する。
- 標準パレットのクラス（例：`bg-indigo-500`、`text-slate-400`）を直接使うことを禁止する。
- `rounded-*` と `shadow-*` は自前で定義した段階のみ使う。

### 4.7 アニメーション（`motion-web.md`）

ライブラリの使い分け：

- **Motion**（旧 Framer Motion、`motion/react`）：アプリ系の細かな動き（メニューの開閉、トグル、並び替え、画面遷移）。
- **GSAP**（ScrollTrigger、SplitText）：サイト系のスクロール演出、文字単位の演出。
- **Lenis**：サイト系の慣性スクロール。必要な場合のみ使う。

数値の初期値（スキル作者の調整欄として表にまとめる）：

| 項目 | アプリ系 | サイト系 |
|---|---|---|
| 所要時間 | 120〜240ms | 600〜1200ms |
| 文字・要素ごとの遅延 | 20〜40ms | 40〜80ms |
| イージング | 減速カーブ（例：`cubic-bezier(0.22, 1, 0.36, 1)`） | 用途別に定義（登場、退場、スクロール連動） |

共通ルール：

- ブラウザ標準の `ease` や `linear` を理由なく使わない。
- すべての要素を同じ速さ・同じ方向・同じ遅延で動かさない。
- `prefers-reduced-motion` に必ず対応する。

数値の初期値はモデルの知識をもとに記述し、スキル作者が後から調整する。将来の `motion` スキル（動画）とは役割を分け、`web` はブラウザ上の UI とスクロールの動きを扱う。

### 4.8 禁止リスト（`anti-patterns.md`）

各項目に「禁止事項」と「理由」をセットで記載する。3段階で管理する。

**絶対禁止**

- 紫〜青のグラデーション背景
- グラデーションのかかった文字
- 角丸カード＋薄い影の3列配置
- 定型的な中央寄せヒーロー（大見出し＋サブ文＋ボタン2つ）
- Inter / Poppins / Roboto など定番フォントのみで組むこと
- 「🚀 Fast」のような絵文字＋形容詞の特徴リスト、絵文字のアイコン代用
- 意味のないぼかした光の玉（blob）の背景
- ダークモード＋ネオンの発光
- 均等すぎる余白（メリハリのない間隔）
- ボタンやリンクに文字の矢印（`→` `↗` `›` `»` `▼` など）を入れること。代わりに Iconify の SVG アイコンを使う。理由は、文字の矢印はフォントによって太さや位置がずれ、サイズ・色・動きを細かく制御できないためである
- Tailwind 標準パレットのクラスを直接使うこと

**条件付き（機能上の理由を言語化できる場合のみ使う）**

- ガラス風の半透明（glassmorphism）：写真や動画など情報量の多いものの上に操作パネルを重ねる場合に限る。装飾目的の使用は禁止する
- 複数のアクセントカラー：UI の色と中身の色（例：トラックの種類、カテゴリ）を分けて定義する場合に限る

**要注意（既定では避け、使う場合は理由を示す）**

- 見出しの上の小さいピル型ラベル（「New」など）
- 一律のふわっと表示。ただし「全要素が同じ速さ・方向・遅延」は絶対禁止とする
- 料金表の中央プランだけを拡大し「Most Popular」バッジを付ける構成

禁止リストは、スキルなしの出力へのダメ出し（8章）によって随時追加する。

### 4.9 自動チェック（`lint-design.mjs`）

生成されたコード（`.tsx`、`.jsx`、`.css`、`.html`）を走査し、次のパターンを検出する。

- ボタンやリンクの中にある文字の矢印
- アイコン代わりの絵文字
- Tailwind 標準パレットのクラス
- 紫〜青のグラデーション、グラデーション文字（`bg-clip-text` と `bg-gradient-*` / `bg-linear-*` の組み合わせ）
- フォント指定が Inter / Roboto / Poppins / Arial / system-ui のみのもの
- ブラウザ標準のままの `<select>` と `<input type="number">`
- `prefers-reduced-motion` に対応していないアニメーション
- `transition: all`（`transition-all`）、イージングの未指定

出力形式は「ファイル名:行番号、ルール名、違反の理由」とし、AI がそのまま修正に使えるようにする。違反があれば終了コードを非ゼロにする。構図や余白の良し悪しなど機械で判定できないものは、スクリーンショットによる自己批評（`critique.md`）に任せる。

### 4.10 スクリーンショット（`screenshot.mjs`）

Playwright を用い、指定した URL またはローカルの HTML について、PC 幅（1440px）とスマートフォン幅（390px）、指定したテーマごとにスクリーンショットを撮る。画像は作業用ディレクトリに保存し、リポジトリには含めない。

## 5. 参考実例と観察記録

### 5.1 著作権・ライセンスの取り扱い

`references/` には実物のコピーを一切入れない。観察して自分の言葉と数値に置き換えたものだけを入れる。

- 入れてよいもの：数値の観察結果、原則の言語化、フォント名・ライブラリ名、匿名化した出典ラベルと観察日。
- 入れないもの：サイトの HTML・CSS・JS（一部分も含む）、画像、ロゴ、写真、文章、フォントファイル、スクリーンショット。
- スクリーンショットは分析時に作業用ディレクトリで一時的に扱うのみとし、リポジトリには含めない。利用者から提供されたスクリーンショットには個人名やメッセージが含まれるため、分析結果以外は保存しない。
- スキルには「〇〇のサイトのようにする」という指示を書かず、抽出した原則と数値の幅のみを渡す。
- 1つの実例の数値をまとめて移植せず、複数の実例から傾向として抽出する。

数値や手法などのアイデア・事実は自由に利用でき、具体的な表現（コード・画像・文章）は保護される、という線引きに基づく。配布範囲を広げる際は、必要に応じて専門家に確認する。

### 5.1.1 実例名の匿名化

- スキルのファイル（`skills/` 以下）と設計書では、実例のサービス名・アプリ名・サイト名を書かず、「サイト1（個人のポートフォリオ）」「アプリA（チャット）」のように、匿名のラベルと種類で表す。
- 実例とラベルの対応表はリポジトリに含めず、スキル作者の手元でのみ管理する。
- デザイン作業や分析の過程で実例を直接参照する必要がある場合（ブラウザで開いて数値を測る場合など）は、作業中に限り実名・URL を使ってよい。ただし、その結果をファイルに書き出す際は匿名ラベルに置き換える。
- 公開されている一般的な技術情報（ライブラリ名、フォント名、Web 標準の仕様名）は匿名化の対象外とする。

### 5.2 サイト系の実例（`observations/site.md`）

実装時にブラウザで直接分析する。対象はスキル作者が選んだサイト4件と、Web デザインのギャラリーサイト1件（実例そのものではなく、実例を探す場所として扱う）である。URL はスキル作者の手元の対応表で管理する。

### 5.3 アプリ系の実例（`observations/app.md`）

スキル作者が提供したスクリーンショット（2026-10-03）の分析結果を記録する。

| 実例 | 主な観察 |
|---|---|
| アプリA（ゲームのランチャー） | アクセントの緑を、主要な操作・選択中・ON 状態・ダウンロードにだけ使い、残りはグレーの段階で組む。一覧の各行は「名前（太字・明るい）＋補足（細字・グレー）」の2段 |
| アプリB（開発者向けダッシュボード） | 黒背景の中で主要ボタンだけを白地に黒文字にし、色を足さずに主役を示す。カードは影ではなく 1px の枠線と背景の明度差で区切る。検索欄にショートカットキーを表示する |
| アプリC（オンラインホワイトボード） | キャンバスの上に浮くツールバーにだけ影と大きめの角丸を付ける。影を「浮いている」という意味を伝えるために使う |
| アプリD（チャット） | 情報量が多くても、太さと色の差で階層を作るため散らからない。見出しに件数を付ける。行ごとの操作はホバー時のみ表示する |
| アプリE（AI チャット） | 純粋な黒ではなく、わずかに暖かみのある黒の背景。あいさつの見出しにのみセリフ体を使う。アクセントカラーはロゴマークのみに使う。お知らせに閉じるボタンとその場でできる操作をセットで置く |
| アプリF（モーショングラフィックス制作ツール） | 数値パラメータの1行を「アイコン＋ラベル＋スライダー＋数値入力＋単位＋リセット」で統一する。数値表示は等幅フォント。UI の色（シアン＝選択中）と中身の色（トラックの種類）を分ける。パネルを角丸の島として浮かせ、隙間で区切る。セクション見出しを「点＋字間を広げた大文字」で統一する |

共通して見られる原則：

1. アクセントカラーは1色に絞り、使う場所を限定する。
2. 色を足さず、明暗の反転で主役を示す方法がある。
3. 影は浮いているものにだけ使う。
4. 文字の階層はサイズより太さと色で作る。
5. 操作のヒント（ショートカットキー、件数）を画面に出す。
6. アイコンとラベルは原則セットにする。アイコン単独は意味が定番化した場所に限る。

### 5.4 直感的な UI の原則（`intuitive-ui.md`）

大手 OS メーカーの公式サイトと、同社が公開している UI ガイドラインを分析し、原則を自分の言葉で要約する。丸写しはしない。

### 5.5 和文と欧文の組み合わせ（`typography-ja.md`）

日本語中心・英語混在を前提に、和文フォントと欧文フォントの組み合わせ表を作る。定番（Noto Sans JP 単独、Inter 単独など）を避けた候補を、印象（静か、精密、遊びがある等）ごとに整理する。和文・欧文それぞれの字間・行間の初期値も記載する。

## 6. 調整欄の仕組み

- **スキル作者の調整欄**：各 `references/` ファイル内の表にある初期値。スキル作者が育てていく。
- **ユーザーの調整欄**：`design-core/user-preferences.md`。利用者はこのファイルだけに書き込む。初期状態は空のひな形とする。
- **優先順位**：プロンプトでの指示 ＞ ユーザーの調整欄 ＞ スキル作者の調整欄。

利用者が作者側のファイルを直接編集せずに済むため、スキル作者がスキルを更新して配布し直しても、利用者の設定は失われない。

## 7. エラー時の扱い

- `lint-design.mjs` が違反を出した場合：違反がゼロになるまで修正する。意図的な例外（例：条件付き項目の正当な使用）は、直前の行に `design-lint-disable-next-line <ルール名> -- <理由>` 形式のコメントを書くことで抑制できるようにする。理由のない抑制コメントは、それ自体を違反として扱う。
- スクリーンショットが撮れない場合（ブラウザが使えない環境など）：その旨を報告に明記し、自動チェックとコードの読み直しによる検証で代替する。撮れたことにはしない。
- 自己批評2周の後も残った問題：修正を続けず、報告で正直に伝える。

## 8. スキル自体の検証

「スキルなし」と「スキルあり」で同じお題を生成して比較する。

1. お題を4つ用意する：サイト系2つ（例：イラストレーターのポートフォリオ、カフェのサイト）、アプリ系2つ（例：設定画面付きのダッシュボード、動画編集ツールのパラメータパネル）。
2. スキルなしで生成し、スクリーンショットと `lint-design.mjs` の結果を記録する。これを AI っぽさの教材としても使う。
3. スキルありで生成し、同様に記録する。
4. 合格基準：
   - スキルありの出力で、自動チェックの違反がゼロである。
   - スキル作者がスクリーンショットを見比べ、4つ中4つでスキルありの方がAI感が薄いと判断する。
5. スキル作者のダメ出しを、`anti-patterns.md` または `critique.md` に追加する。

`lint-design.mjs` 自体は、違反を含むサンプルと含まないサンプルを用意し、検出の有無をテストで確認する。
