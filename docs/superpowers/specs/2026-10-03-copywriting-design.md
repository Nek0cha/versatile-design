# 設計書：文章のスキル（copywriting）

- 作成日：2026-10-03
- 状態：レビュー待ち
- 対象サブプロジェクト：第2弾（`copywriting`）

## 1. 目的

キャッチコピーと LP の本文を、AI っぽさのない形で生成するスキルを作る。

現在は外部の文章スキル（仕事の文書を自然な日本語にするもの）を使っているが、次の理由で置き換える。

- 外部スキルは議事録や報告書のような「論理が明快で読みやすい文書」を対象にしている。キャッチコピーに必要な「印象に残る」「意味が二重になる」といった性質は扱っていない。
- AI っぽさの主な原因は、言い回しよりも型と中身にある。どの商品にも当てはまる言葉を型に流し込むと、文法が自然でも AI っぽく見える。

### 1.1 成功の基準

- 同じお題をスキルなし／スキルありで生成し、両方の案を混ぜて並べたとき、スキル作者が「好き」に選ぶ案の多くがスキルありの案になる（8章）。
- スキルありの出力で、自動チェック（`lint-copy.mjs`）の違反がゼロになる。

### 1.2 前提

- 利用者は基本的にスキル作者本人である。
- 好みは全開で作る。他の利用者が上書きできる調整欄を持たせる（6章）。
- 出力する文章は日本語が中心である。技術系やクリエイター系のサイトでは英語のキャッチコピーも使う。
- `copywriting` は単独でも使えるようにする。`design-core` を読まなくても動く。

## 2. 範囲

| 対象 | 今回 |
|---|---|
| キャッチコピー（メインコピー） | 作る |
| サブコピー（キャッチの下の一文） | 作る |
| LP の本文（セクションの見出しと説明文） | 作る |
| マイクロコピー（ボタン、フォームのラベル、エラー文など） | 将来 |
| 長い記事、ブログ、仕事の文書 | 対象外 |

## 3. ファイル構成

```
skills/copywriting/
├── SKILL.md                      手順：聞き出し → 素材の整理 → 量産 → 検査 → 5案の提示 → 本文
├── user-preferences.md           ユーザーの調整欄（初期状態は空のひな形）
├── references/
│   ├── hearing.md                聞き出しの質問と、追加質問の出し方
│   ├── angles.md                 5つの切り口とその書き方
│   ├── taste.md                  スキル作者の好み（判定結果から抽出した原則）
│   ├── anti-patterns.md          避ける型、空っぽの言葉、本文の禁止事項
│   ├── english.md                英語のキャッチコピーの使いどころと禁止事項
│   ├── body.md                   LP の本文の書き方
│   └── critique.md               自己批評の項目（差し替えテストを含む）
└── scripts/
    └── lint-copy.mjs             避ける型と空っぽの言葉の検出
```

`references/` は毎回すべてを読ませず、手順の中で必要になった時点で必要なファイルだけを読ませる。

## 4. 各要素の設計

### 4.1 作業の流れ（`SKILL.md`）

1. **読み込み**：`user-preferences.md` と `references/taste.md` を読む。
2. **聞き出す**（4.2節）：1回目の質問を出す。答えが薄い場合に限り、追加の質問を1問だけ出す。質問は最大2回とする。
3. **素材を整理する**：答えから「この商品やサービスにしか言えない事実」を3つ書き出す。数字、モノの形、使う場面、作り手のこだわりなどである。以降の案は、必ずこの3つのどれかを根っこに持つ。
4. **量産する**（4.3節）：5つの切り口それぞれで4〜6案、合計20〜30案を作業用ファイルに書く。この段階では利用者に見せない。
5. **検査する**：`lint-copy.mjs` を作業用ファイルに対して実行し、違反した案を落とすか直す。残った案に `critique.md` の差し替えテスト（4.5節）をかける。
6. **5案を提示する**：切り口ごとに1案ずつ、合計5案を出す。各案には次を付ける。
   - サブコピー（1文）
   - 狙い（どの事実を根っこにしたか、どの切り口か。1行）
7. **利用者が選ぶ**：選ばれた案で確定する。「2番と4番の間」のような指示があれば、そこから作り直す。
8. **本文を書く**（LP の本文を頼まれた場合）：選ばれたキャッチの方向に合わせて、`body.md` に従って書く。書いたら再び `lint-copy.mjs` を実行する。

### 4.2 聞き出し（`hearing.md`）

1回目の質問は1つのメッセージにまとめ、なるべく選択式にする。選択式の質問ツールが使える環境ではそれを使う。

| 質問 | 形式 |
|---|---|
| 何を書くか（キャッチだけ／キャッチと本文） | 選択式 |
| 何のためのコピーか（商品やサービスの名前と一言の説明） | 自由記述 |
| 一番伝えたいこと（機能や性能／使ったときの気持ち／作り手のこだわり／手軽さや価格／世界観） | 選択式。自由記述も可 |
| 手元にある素材（具体的な数字、お客さんの言葉、作った理由など） | 自由記述。なくてもよい |

依頼の文面ですでに分かっている項目は聞かない。

**答えが薄いときの追加質問**：「手軽さ」を選んだだけのように、3節の「この商品にしか言えない事実」が1つも取り出せない場合に限り、追加の質問を1問だけ出す。例：「例えば、どんな場面で手軽さを感じてもらいたい？」。追加の質問のあとは、答えが薄くても先に進む。

### 4.3 5つの切り口（`angles.md`）

5案はすべて違う切り口で出す。選ぶ楽しさと、方向の比べやすさを優先するためである。

| 切り口 | 考え方 |
|---|---|
| モノの事実 | 商品の形や数を一語で言い切る。その商品でしか成り立たない語を使う |
| 反転 | 同じ語を肯定と否定で並べ、意味をひっくり返す |
| 意味の二重化 | 一つの語に二つの意味を乗せる。商品の性質と、受け手の気持ちの両方に掛かる語を探す |
| 文法の崩し | 品詞や助詞をあえてずらし、引っかかりを作る |
| 場面 | 商品を使う瞬間や、その前後の情景を切り取る |

**英語の案**：サイトの種類が技術系やクリエイター系の場合、5案のうち1〜2案を英語にする（`english.md`）。英語の案にも切り口を割り当て、日本語のサブコピーを添えてよい。

### 4.4 スキル作者の好み（`taste.md`）

スキル作者が既存のコピー30本（うち5本はAIが作った空っぽのコピー）に「好き」の印を付けた結果から、原則を抽出して記録する。コピーの本文と企業名は書かない（5章）。

**好む性質**

- 短くて静か。叫ばない。
- 言い切る。
- 意味が二重になる言葉遊び。商品の性質と受け手の気持ちの両方に掛かるもの。
- 文法を少しずらした引っかかり。
- 少し知的なひねり。説明しすぎず、受け手に考える余地を残す。

**好まない性質**

- 音だけのダジャレ（意味が重ならない語呂合わせ、社名の語呂合わせ）。
- 勢いや叫び（感嘆、詰問）。
- 古い性別の役割を前提にした表現。
- 三つ並べ（「〜く、〜く、〜く。」）。

**判定の教訓**：静かで短く言い切る形のAI製コピー1本に、スキル作者が「好き」を付けた。見た目が好みに合っていると、中身が空っぽでも人の目は通してしまう。空っぽの言葉は、人の判定に頼らず機械で検出する（4.6節）。

**英語でも同じ物差しを使う**：スキル作者が好む英語のコピーも、3〜4語で静かに言い切り、意味の二重化か文法の崩しを使っている。日本語と英語で別の好みは設けない。

### 4.5 自己批評（`critique.md`）

- **差し替えテスト**：案の中の商品名やサービス名を、同じ業種の別の会社に置き換えても成り立つか確かめる。成り立つ案は落とす。型そのもの（例：「〜を、〜で。」）は禁止せず、型の空欄にどの商品にも言える言葉が入っている場合だけを落とす。
- **言葉遊びの確認**：言葉遊びは、意味が二重になる場合だけ使う。音だけが似ている語呂合わせは使わない。
- **事実の確認**：案の根っこにある事実が、4.1節の手順3で書き出した3つのどれかに当たるか。
- 自己批評は最大2周で止める。それ以上は無難な方向に収束しやすいためである。

### 4.6 避けるもの（`anti-patterns.md`）

**空っぽの言葉**（どの商品にも言える言葉）

- 日本語の例：価値、特別、可能性、未来、すべての人、あなたらしさ、新しい、体験、毎日、想い、寄り添う、革新、次世代、加速、次のレベル
- 英語の例：Unlock、Elevate、Empower、Seamless、Supercharge、Revolutionize、Transform、Effortless、Next level、Journey

これらの語は、事実を表す語と組み合わせて使う場合に限り、理由を書いて許可する（7章の抑制コメント）。

**避ける型**

- 「〜を、もっと〜に。」のように、空欄が抽象語で埋まる型
- 「〜だけじゃない。〜も。」
- 「AではなくB」で、AもBも抽象語のもの
- 三つ並べ
- 英語の「Not just X. Y.」「Where X meets Y」「X, reimagined」

**AI 製の空っぽのコピーの例**（スキル作者の判定に使ったもの。AI が作ったため本文を載せてよい）

- 毎日を、もっと特別に。
- あなたらしさを、もっと自由に。
- その一杯が、明日を変える。
- 心と体に、やさしい毎日を。
- 新しい価値を、すべての人へ。

### 4.7 LP の本文（`body.md`）

読みやすさより「人が書いた感じ」を優先する。

- 言い切りを多くする。「〜できます」「〜が可能です」「〜することができます」を減らす。
- 同じ文末を3回続けない。
- 文の長さをそろえない。短い文と長い文を混ぜる。
- 一般論で始めない（「近年、〜が注目されています」など）。
- 「と言えるでしょう」「ではないでしょうか」「さまざまな」「多様な」を使わない。
- セクションの見出しもキャッチコピーと同じ基準で書く。
- 架空の実績の数字や架空の推薦文を作らない。素材にない数字は「ここに数字」と置く。

### 4.8 英語のキャッチコピー（`english.md`）

- 使う場面：技術系、クリエイター系、海外の利用者も想定するサイト。
- 長さ：3〜5語を目安にする。
- 4.6節の英語の空っぽの言葉と型を使わない。
- 意味の二重化（業界用語と一般の意味が重なる語）か、文法の崩しを優先する。
- 日本語のサブコピーを添えてよい。英語の直訳にはしない。

### 4.9 自動チェック（`lint-copy.mjs`）

`.md`、`.txt`、および `.tsx`、`.jsx`、`.html` のテキスト部分（JSX のテキストと文字列リテラル）を走査し、次を検出する。

- 空っぽの言葉（4.6節）
- 避ける型（正規表現で検出できるもの）
- 本文の禁止表現（4.7節）
- 同じ文末の3回連続
- 「〜できます」「〜が可能です」の割合が、本文の文末の3割を超える場合

出力形式は `design-core` の lint と同じく「ファイル名:行番号、ルール名、違反の理由」とし、違反があれば終了コードを非ゼロにする。差し替えテストのように機械で判定できないものは、自己批評（4.5節）に任せる。

`web` の lint のエンジン（ルールの登録、抑制コメントの解釈、出力形式）を共通化できる場合は共通化する。

### 4.10 `web` スキルとのつながり

`copywriting` ができたら、`web` でページを作るときに `copywriting` を呼ぶ。

- `web` の段階2（コンセプトを決める）で、利用者が文章を渡していない場合に限り、`copywriting` の聞き出し（4.2節）を同じメッセージで行う。
- `web` は「確認のために止まらず進める」方針のため、5案の提示では利用者の選択を待たない。5案のうち `copywriting` が最も推す1案でページを作り、残りの4案は最後の報告に並べて、差し替えられるようにする。
- マイクロコピー（ボタンなど）は今回の範囲外のため、`design-core/SKILL.md` の5節（仮の文章の扱い）のルールを引き続き使う。
- `design-core/SKILL.md` の5節の冒頭「文章を生成するスキルはまだない」を、`copywriting` の範囲を示す記述に書き換える。`web/SKILL.md` の該当行も合わせて直す。README のスキル一覧の状態も更新する。

## 5. 著作権と実例名の扱い

`design-core` と `web` の設計書の5.1節、5.1.1節と同じ方針をとる。

- `skills/` 以下と設計書には、実在のコピーの本文を入れない。観察して抽出した原則だけを入れる。
- 実在のコピーの企業名や商品名を書かない。必要な場合は「手本A（飲料）」のように匿名のラベルで表す。
- スキル作者が印を付けた30本のリストと、その判定結果の原本はリポジトリに含めない。
- AI が作ったコピー（4.6節の例など）は、実在の表現ではないため載せてよい。

## 6. 調整欄の仕組み

- **スキル作者の調整欄**：`taste.md`、`anti-patterns.md` などの初期値。
- **ユーザーの調整欄**：`copywriting/user-preferences.md`。初期状態は空のひな形とする。
- **優先順位**：プロンプトでの指示 ＞ ユーザーの調整欄 ＞ スキル作者の調整欄。

## 7. エラー時の扱い

- `lint-copy.mjs` が違反を出した場合：違反がゼロになるまで直す。意図的な例外は、直前の行に `copy-lint-disable-next-line <ルール名> -- <理由>` 形式のコメントを書いて抑制できる。理由のない抑制コメントは、それ自体を違反として扱う。
- 聞き出しで素材がほとんど得られなかった場合：追加の質問のあとは先に進み、どの案が推測にもとづくかを提示のときに明記する。
- 自己批評2周の後も残った問題：直し続けず、提示のときに正直に伝える。

## 8. スキル自体の検証

手本の判定と同じ「混ぜて印を付ける」形式で行う。スキル作者の手間を減らすためである。

1. お題を4つ用意する：カフェ、イラストレーターのポートフォリオ、開発者向けツール（英語の案が出る想定）、地域の小さな工務店。
2. 各お題について、スキルなしで5案、スキルありで5案を作る。
3. 10案の順番を混ぜ、どちらのものか伏せてスキル作者に見せる。スキル作者は「好き」の番号だけを答える。
4. 合格基準：
   - スキルありの出力で、自動チェックの違反がゼロである。
   - 4つのお題すべてで、「好き」に選ばれた案の過半数がスキルありの案である。
5. 判定のあと、どれがスキルありかを明かし、スキル作者の感想を `taste.md` または `anti-patterns.md` に追加する。

`lint-copy.mjs` 自体は、違反を含むサンプルと含まないサンプルを用意し、検出の有無をテストで確認する。

## 9. 将来の予定

- マイクロコピー（ボタン、フォームのラベル、エラー文、空の状態の文）。
- 手本の判定を続け、`taste.md` を育てる。
