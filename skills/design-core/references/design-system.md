# デザインシステムの引き継ぎと書き出し

プロジェクトにすでに見た目の系統があるときと、利用者に「デザインシステムを書き出して」「DESIGN.md を作って」「トークンを整理して」と頼まれたときに読む。別の会話や別の画面を作るときにも、同じ見た目の系統を保つためである。

## 1. 作業の最初に確かめる

- プロジェクトのルートに `DESIGN.md` があれば、コンセプトを決める前に読む。そこに書かれた色、書体、角丸、余白、部品の扱い、Do's and Don'ts を引き継ぐ。画面を足すときに、新しい見た目の系統を作らない。
- `DESIGN.md` がなくても、コードに一貫した系統（`@theme` や CSS 変数のトークン、共通の部品）があれば、それを引き継ぐ。ファイルがないことは、系統がないことを意味しない。
- 作り直しを頼まれた場合（`../web/references/refine.md` の1節）は、今の系統を手本にしない。中身と機能だけを引き継ぎ、作り終えたら報告で `DESIGN.md` の更新を提案する。
- プロンプトでの指示が `DESIGN.md` と食い違う場合は、SKILL.md の2節の優先順位どおりプロンプトに従い、報告で `DESIGN.md` の更新を提案する。

## 2. 部品とトークンにまとめる基準

既存の画面の系統を整理するよう頼まれたとき、または直す途中で値がばらついているのを見つけたときの判断基準である。頼まれていないのに、プロジェクト全体を作り替えない（`../web/references/refine.md` の3節）。

- 探す対象：
  - 繰り返す部品（ボタン、カード、入力欄）
  - 直接書かれた色、余白、書体、影の値
  - 同じ概念の別々の実装
  - 繰り返す組み方（フォームの行、ツールバーのまとまり、空の状態）
  - 繰り返す文字の組（サイズ、太さ、行間の組み合わせ）と、繰り返す動き（イージング、所要時間）
- 同じ意図で3回以上使われているものだけをまとめる。1回きりの値や、その場所だけの事情による値はまとめない。早すぎる共通化は、重複より害が大きい。
- 見た目が似ていても、意図が違うものは分けたままにする（例：送信のボタンと、絞り込みの切り替えのボタン）。
- トークンには意味のある名前を付け、値をそのまま名前にしない（`blue-500` ではなく `accent`）。すべての値をトークンにしない。
- 汎用にしすぎない。どこにでも使える代わりに何も決めていない部品は、使う側で毎回作り直されるだけである。
- まとめたら、古い実装をすべて置き換え、使われなくなったコードを消す。置き換えの前後で見た目と動作が変わっていないことを、スクリーンショットで確かめる。

## 3. DESIGN.md を書く

利用者に頼まれたときに書く。頼まれていなければ、新しく見た目の系統を作ったときの報告で「`DESIGN.md` に書き出すか」を1行で提案するだけにする。

- すでにファイルがある場合は、黙って上書きしない。今の内容を見せ、更新・上書き・統合のどれにするかを聞いてから書く。
- 完成した画面から書く。作る前に書いた規則は、実物の説明ではなく、実物に合わないまま守られる決まりになりやすい。
- 書式は Google の DESIGN.md の仕様に合わせる。ほかのツールでも読めるようにするためである。

### 3.1 frontmatter

YAML の frontmatter に、機械が読むトークンを書く。値の正は frontmatter であり、本文はその使い方を説明する。

```yaml
---
name: （プロジェクト名）
description: （1行の説明）
colors:
  accent: "oklch(0.68 0.15 45)"
  surface-0: "oklch(0.17 0.008 60)"
  text-strong: "oklch(0.96 0.005 60)"
typography:
  display:
    fontFamily: "Instrument Serif, Shippori Mincho, serif"
    fontSize: "4.5rem"
    fontWeight: 400
    lineHeight: 1.1
  body:
    fontFamily: "Instrument Sans, Zen Kaku Gothic New, sans-serif"
    fontSize: "1rem"
    fontWeight: 400
    lineHeight: 1.8
rounded:
  sm: "4px"
spacing:
  sm: "8px"
  md: "16px"
components:
  button-primary:
    backgroundColor: "{colors.text-strong}"
    textColor: "{colors.surface-0}"
    rounded: "{rounded.sm}"
    padding: "10px 20px"
---
```

- 最上位に置けるのは `name`、`description`、`colors`、`typography`、`rounded`、`spacing`、`components` だけである。影、動き、ブレークポイントは frontmatter に書かず、本文の該当する節に書く。
- 値と名前は、プロジェクトで正としている書き方に揃える。このスキルで作ったプロジェクトなら、`@theme` のトークン名と `oklch()` の値をそのまま写す（web は `../web/references/tokens-tailwind.md`）。
- `components` の各項目に書ける属性は `backgroundColor`、`textColor`、`typography`、`rounded`、`padding`、`size`、`height`、`width` の8つだけである。状態は `button-primary-hover` のように別の項目にする。値は `{colors.accent}` の形でトークンを参照する。
- 実際に使っているトークンだけを書く。空の段階や、使っていない値を作らない。

### 3.2 本文の節

見出しは次の8つを、この順番で、この英語のまま使う。ツールが見出しの文字列で読み取るためである。該当しない節は空で置かず、省く。本文は利用者の言語で書く。

| 見出し | 書くこと |
|---|---|
| `## Overview` | 系統全体を、名前の付いた1つの比喩で表す（例：「実験ノート」「古い時刻表」）。コンセプトの3行、密度、全体の考え方を2〜3段落で書き、最後に主な特徴を箇条書きにする |
| `## Colors` | 役割ごと（Primary、Neutral など。アクセントが1色なら Secondary と Tertiary は省く）に、説明的な色の名前、値、どこでなぜ使うか |
| `## Typography` | 書体の組とその性格。display・headline・title・body・label の段階ごとに、太さ、サイズ、行間、用途 |
| `## Layout` | 格子、外側の余白、密度、幅による変化、余白の段階 |
| `## Elevation & Depth` | 影を使うか、明度の差で奥行きを出すか。影の種類と使う場所。影を使わないなら、そう明記する |
| `## Shapes` | 角丸、線、切り抜きなどの形の言葉 |
| `## Components` | 実在する部品だけ。部品ごとに性格を1行書き、形、色の割り当て、状態（ホバー、フォーカス、エラー、無効）を書く |
| `## Do's and Don'ts` | 「Do」「Don't」で始まる具体的な指示。値が決まっているものは値も書く |

### 3.3 書き方

- 名前の付いた規則を、各節に1〜3個書く。形は「**〜の規則**：（短く強い指示）」である。例：「**一声の規則**：アクセントは1画面の5%以下にする。少ないことに意味がある」。箇条書きの原則より引用しやすく、後で作業するモデルに守られやすい。
- 説明を先に、値を括弧で後に書く。「ゆるく丸めた角（4px）」のようにし、クラス名（`rounded-sm`）をそのまま書かない。
- 何であるかより、どこでなぜ使うかを書く。
- 確かな決まりは強く、まだ仮の決まりは弱く書き分ける。
- 本文に値を書く場合は、frontmatter と同じ値にする。違う値を2か所に書かない。
- 実在しない部品を作らない。ボタンとカードしかないなら、その2つだけを書く。
- 製品の事業や戦略の説明を入れない。`DESIGN.md` は見た目だけを扱う。
- 1つの画面だけの事情（その画面のコンセプトや配置）を、系統全体の決まりにしない。
