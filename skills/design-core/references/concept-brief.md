# コンセプトの決め方

コードを書く前に、この手順でコンセプトを決める。サイト系では案を出して利用者に選んでもらい、アプリ系では宣言して進める。どちらにするかは5節の表に従う。

## 1. 3行のコンセプト

### 誰に

- 使う人・見る人を、状況まで含めて1文で書く。「誰が、どんな場面で、何のために見るか」が分かる形にする。
- 「すべての人」「ユーザー」「若い世代」のような、誰も絞り込まない言い方をしない。
- 依頼文に書かれていなければ、お題から最も可能性の高い1人を選んで書く。

### どんな印象を

- 形容詞を2〜3個書く。
- 次の語は単独では使わない。誰にでも当てはまり、判断の基準にならないためである：モダン、洗練された、シンプル、クリーン、おしゃれ、スタイリッシュ、プロフェッショナル、ミニマル、直感的、美しい。
- 少なくとも1つは、手触りや温度など感覚に訴える語にする（例：紙のような、ひんやりした、乾いた、柔らかい）。
- 2つの語の間に少し緊張関係があると、平均から離れやすい（例：「静か、でも少しいたずら」「精密、でも冷たくない」）。
- 確認：同じ業種の他社にもそのまま当てはまる形容詞なら、書き直す。

### 何で記憶に残すか（記憶のフック）

- 見終わった後に「あの〇〇の画面」と思い出せる要素を1つだけ決める。
- 名詞で書け、スクリーンショットの上で指させるものにする（例：画面幅いっぱいの縦書きの見出し、行ごとに色の付いたタイムライン）。
- 「美しいデザイン」「使いやすさ」は要素ではないのでフックにならない。
- サイト系では最初の画面（スクロール前）に置く。アプリ系では最もよく使う画面に置く。

## 2. 良い例と悪い例

| お題 | 悪い例 | 良い例 |
|---|---|---|
| イラストレーターのポートフォリオ | 誰に：すべての人／印象：モダンで洗練された／フック：美しいデザイン | 誰に：書籍の装丁を依頼する先を探している編集者／印象：静か、紙の手触り、少しいたずら／フック：作品1点を画面いっぱいに置き、余白の隅に手書きの通し番号を添える |
| 個人経営のカフェのサイト | 誰に：カフェが好きな人／印象：おしゃれでスタイリッシュ／フック：おいしそうな写真 | 誰に：近くで働き、平日の昼に一人で入れる店を探す会社員／印象：乾いた木の温かさ、落ち着いた、少し朴訥／フック：その日の豆と焼き菓子を黒板の書き文字風に並べた日替わりの一覧 |
| 設定画面付きのダッシュボード | 誰に：ユーザー／印象：シンプルで直感的／フック：使いやすい UI | 誰に：毎朝5分で前日の数字を確認するチームの責任者／印象：精密、静か、冷たくない／フック：前日比を等幅数字で揃え、悪化した行にだけアクセントの印を付けた一覧 |

## 3. サイト系とアプリ系の判定

「良いデザイン」の基準がほぼ逆であるため、画面ごとにどちらかに判定する。判定によって媒体別スキルで読む資料が変わる。

| | サイト系 | アプリ系 |
|---|---|---|
| 例 | ポートフォリオ、企業サイト、LP | ダッシュボード、ツール、設定画面 |
| 目的 | 記憶に残る、世界観を伝える | 迷わず操作できる、毎日使っても疲れない |
| 見せ場 | 大胆なタイポグラフィ、余白、スクロール演出 | 部品の作り込み、状態の伝え方、情報の密度 |

- 判定の問い：「その画面は、一度見てもらうことが目的か（サイト系）、繰り返し操作されることが目的か（アプリ系）」。
- 両方の性質を持つ依頼（例：アプリの紹介 LP と管理画面の両方）は、画面ごとに判定する。1つの画面の中で混ぜない。

## 4. テーマの決め方

1. プロンプトに指定があればそれに従う（例：「ダークのみ」「ライト基本」「ライトのみ」）。
2. プロンプトに指定がなければ、ユーザーの調整欄の「テーマの既定」に従う。
3. どちらにもなければ「ダーク基本＋ライト対応」にする。

どの場合も、色はトークンで定義し、テーマごとに値を差し替えられる構造にする（`references/color.md` の5節）。「ダークのみ」の指定でも、色を直接書かずトークン経由にする。

## 5. 確認の流れ

| 状況 | コンセプト | 技術スタック |
|---|---|---|
| 新規・サイト系 | 案を 2〜3 個出して選んでもらう（6節） | 提案して確認する。案と同じメッセージで出す |
| 新規・アプリ系 | 宣言して進める（7節） | 提案して確認する |
| 既存のプロジェクト・サイト系 | 案を 2〜3 個出して選んでもらう（6節） | 既存のものに合わせ、質問しない |
| 既存のプロジェクト・アプリ系 | 宣言して進める（7節） | 既存のものに合わせ、質問しない |
| プロンプトに「おまかせ」「確認なしで」「任せる」などがある | 最も良い案を自分で選び、選んだ理由を1文添えて宣言して進める（7節） | 自分で選び、理由を添えて宣言して進める |

- 新規か既存かは、作業ディレクトリに `package.json` があるかどうかで判定する。
- 案や技術スタックを質問したら、回答があるまでコードを書かない。
- 利用者が案を組み合わせたり直したりした場合（「案2のフックで、印象は案1」など）は、その内容で7節の宣言を出してから進める。
- サブエージェントとして動いている場合など、質問しても答える人がいない場合は「おまかせ」と同じに扱う。答える人がいるかどうかは、呼び出し元の指示（「質問せずに完成まで進める」「サブエージェントとして動く」など）で判断する。指示から分からなければ、答える人がいるものとして質問する。
- 技術スタックの決め方は媒体別スキルの資料に従う（web は `../web/references/stack.md`）。

## 6. 案の書式

案同士は、記憶のフックの種類を変える（例：巨大な文字、写真の配置、WebGL の面）。形容詞だけが違う案を並べない。動きの強さは記憶のフックから決め、フックが動きや 3D そのものである案だけを「GSAP の演出あり」「Three.js あり」にする。

```
案1：（案を一言で表す名前）
- 誰に：（1文）
- どんな印象を：（形容詞2〜3個）
- 何で記憶に残すか：（要素を1つ）
- 動きの強さ：静か／GSAP の演出あり／Three.js あり
- 書体の組：（typography-ja.md の記号と、見出しの書体名）
- テーマ：（4節で決めたもの）

案2：…

技術スタック：（提案するもの）。理由：（1文）。次点：（1つ）

どの案にしますか。組み合わせや修正の指定もできます。
```

## 7. 宣言の書式

アプリ系と「おまかせ」の場合、および案が選ばれた後に、次の書式で宣言する。宣言したら止まらずに次の段階（トークン）へ進む。

```
コンセプト
- 誰に：（1文）
- どんな印象を：（形容詞2〜3個）
- 何で記憶に残すか：（要素を1つ）
- 種類：サイト系／アプリ系（画面ごとに異なる場合は画面名と種類を並べる）
- テーマ：ダーク基本＋ライト対応（指定があればその内容）
- 動きの強さ：静か／GSAP の演出あり／Three.js あり（サイト系のみ）
- 書体の組：（typography-ja.md の記号。この時点で決めていなければ「トークンの段階で決める」）
- 技術スタック：（新規の場合のみ。既存の場合は「既存の構成に合わせる」）
- 選んだ理由：（「おまかせ」の場合のみ。案と技術スタックを選んだ理由を1文ずつ）
```
