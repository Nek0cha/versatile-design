# design-core

見た目を作るすべての依頼に共通する思想と手順である。媒体ごとの具体的な作り方（Web なら React と Tailwind の書き方など）は媒体別スキルに書かれている。このファイルは最初に読み、媒体別スキルの手順と合わせて従う。

## 1. このスキルの考え方

- 何も指示がなければ、出力は「平均的で無難なデザイン」に寄る。紫のグラデーション、中央寄せの大見出しとボタン2つ、角丸カードの3列、Inter だけの組版などである。これが「AI 感」の正体である。
- このスキルは、その平均への回帰を、具体的な禁止事項・数値・手順・機械的な検査で止めるためにある。
- 「センスよく」「洗練された」のような抽象的な判断に頼らない。迷ったら、各 references に書かれた数値と禁止事項に戻る。
- 最初に思いついた案は、たいてい平均的な案である。最初の案を採用する前に「同じお題を何も考えずに出したらこうなる」という案を1つ思い浮かべ、それと違う点を1つ以上持たせる。

## 2. 優先順位

指示が食い違ったときは、次の順で上にあるものを採用する。

1. プロンプトでの指示（利用者がその場で書いたこと）
2. `user-preferences.md`（このスキルと同じディレクトリにある。利用者の調整欄）
3. 各 references の「スキル作者の調整欄」にある初期値

`user-preferences.md` は作業の最初に必ず読む。見出しの下が空なら、その項目には好みがないものとして扱い、3 の初期値を使う。

## 3. 作業の流れと、各段階で読むファイル

references は最初にすべて読まない。次の表の段階に来たときに、その段階のファイルだけを読む。文脈を節約し、重要な指示が埋もれるのを防ぐためである。

| 段階 | やること | 読むファイル |
|---|---|---|
| 1. 読み込み | 優先順位を把握する | このファイル、`user-preferences.md` |
| 2. コンセプト | 3行のコンセプト、サイト系／アプリ系、テーマを決めて宣言する | `references/concept-brief.md` |
| 3. トークン | 色、書体、余白、角丸、影、イージングを決める | `references/color.md`、`references/typography-ja.md`（和文と欧文の組み合わせ）、`references/anti-patterns.md` |
| 4. 実装 | トークンだけを使って部品と画面を作る | 媒体別スキルの資料。`references/anti-patterns.md` の禁止事項を守る |
| 5. 検証 | 自動チェック、スクリーンショット、自己批評 | `references/critique.md` |
| 6. 報告 | コンセプト、実施した検証、直しきれなかった点を伝える | なし |

- 段階2は、コードを1行でも書く前に必ず行う。
- 段階3では、`references/anti-patterns.md` を一度通読し、これから決めるトークンが禁止事項に当たらないことを確かめる。
- 段階5の自動チェックとスクリーンショット撮影の方法は媒体別スキルに書かれている。自己批評は最大2周で止める。

## 4. コンセプト先行

- コードを書く前に、「誰に」「どんな印象を」「何で記憶に残すか」の3行を書き、利用者に宣言する。書き方は `references/concept-brief.md` に従う。
- 宣言したら確認を待たずにそのまま進める。依頼が曖昧で3行のどれも決められない場合に限り、質問する。
- 以降のすべての判断（色、書体、余白、動き）は、この3行に照らして選ぶ。3行のどれにもつながらない装飾は入れない。

## 5. 仮の文章の扱い

キャッチコピー、サブコピー、LP の本文は、`copywriting` スキルがあればそれが書く（媒体別スキルの手順に従う）。`copywriting` がないとき、およびボタンやフォームのラベルなどの短い文言は、次のとおりにする。

- 利用者が文章を渡していない場所には、ダミーと一目で分かる仮の文章を置く。例：「ここに見出し」「ここに2行ほどの説明文が入る。」「ボタンの文言」。
- 長さは本番の文章に近づける。見出しなら8〜20文字、説明文なら40〜80文字程度にし、レイアウトの確認に使えるようにする。
- 次のような定型コピーを書かない：「Unlock the power of〜」「Supercharge your〜」「Elevate your〜」「〜を次のレベルへ」「あなたのビジネスを加速する」「シームレスな体験」。
- 架空の実績の数字（「10,000+ ユーザー」など）や架空の推薦文を作らない。必要な場合は「ここに数字」「ここに推薦文」と置く。
- 利用者が文章を渡した場合は、その文章をそのまま使う。言い換えない。

## 6. 媒体を問わない共通原則

実例の観察から得た原則である。詳しい数値は各 references にある。

1. アクセントカラーは1色に絞り、使う場所を限定する（`references/color.md`）。
2. 色を足さず、明暗の反転で主役を示す方法を先に検討する（`references/color.md`）。
3. 高さを表す影は浮いているもの（ツールバー、メニュー、ダイアログなど）にだけ、1種類だけ使う。面の区切りは 1px の線か背景の明度差で行う。ほかに使ってよい影は、装飾としてのぼかさない、ずらした影（`references/anti-patterns.md` の K3）だけである。
4. 文字の階層は、サイズより先に太さと色（グレーの段階）で作る。等幅フォントは桁を揃える数字、コード、ID だけに使い、ラベルや見出しに使わない（`references/anti-patterns.md` の X17）。
5. 余白にはメリハリを付ける。関係の近い要素は狭く、区切りは広くする。すべての間隔を同じ値にしない。
6. アイコンとラベルは原則セットにする。アイコン単独は、意味が定番化した場所（閉じる、検索、設定など）に限る。
7. アプリ系では、操作のヒント（ショートカットキー、件数など）を画面に出す。サイト系には求めない。
8. 状態は例外だけを目立たせる。正常な状態にはラベルも色の点も付けず、異常な状態をアイコン＋文字か、データの印の色で示す（`references/anti-patterns.md` の X18、X20）。

## 7. テーマ

既定は「ダークを基本にし、ライトにも対応する」である。プロンプトか `user-preferences.md` に指定があればそれに従う。どの場合も色はトークンで定義し、テーマごとに値を差し替えられる構造にする（`references/color.md`）。

## 8. 報告

作業の最後に、次の3点を報告する。

1. 宣言したコンセプト（3行、サイト系／アプリ系、テーマ）
2. 実施した検証（自動チェックの結果、撮ったスクリーンショットの幅とテーマ、自己批評の周回数）。スクリーンショットが撮れなかった場合はそう書き、撮れたことにしない。
3. 直しきれなかった点（`references/critique.md` の項目番号を付ける）
