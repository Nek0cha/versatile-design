# 既存の画面を直す依頼

すでにある画面の見た目や使い勝手を直すように頼まれたときに読む。依頼の言葉から目的を1つ決め、その目的の手順書だけを読んで直す。パスは SKILL.md と同じく、スキルのディレクトリを基準にしている。

## 1. この資料を使う依頼

- 作業ディレクトリにある画面について、見た目や使い勝手を変えるように頼まれた場合に使う。例：「設定画面を見やすくして」「トップをもう少し落ち着かせて」「リリース前に仕上げて」「このダッシュボード、どこが悪い？」。
- 作り直しを頼まれた場合（「全部作り直して」「デザインを一新して」）は、この資料を使わない。SKILL.md の手順2から新規として進め、今の画面からは中身と機能だけを引き継ぐ。今の見た目は手本にしない。
- 部品を1つ足すだけの依頼（「ここに検索欄を付けて」）は、その部品のレシピ（SKILL.md の手順4の表）に従って足し、4節の手順5の検証だけを行う。

## 2. 依頼を目的に振り分ける

依頼の言葉を次の表に当てはめ、目的を決める。言い方の例は手がかりであり、同じ意味の言葉なら当てはまる。

| 依頼の言い方の例 | 目的 | 読む手順書 |
|---|---|---|
| 見やすく、分かりやすく、整理して、ごちゃごちゃしている、情報が多すぎる、使いにくい | 見やすくする | `references/refine/clarity.md` |
| 落ち着かせて、うるさい、派手すぎる、目が疲れる、色が多い | 落ち着かせる | `references/refine/quieter.md` |
| 地味、物足りない、印象に残らない、のっぺりしている、安っぽい、ありがちな見た目 | 印象を強くする | `references/refine/bolder.md` |
| 仕上げて、細かいところを整えて、リリース前に見直して、いい感じにして、きれいにして | 仕上げる | `references/refine/polish.md` |
| 壊れにくく、エラーのとき、長い名前のとき、データがないとき、読み込みが遅いとき | 壊れにくくする | `references/refine/harden.md` |
| スマホで崩れる、狭い画面で見づらい、タブレットでも使えるように | 幅に合わせる | `references/refine/responsive.md` |
| どこが悪い？、レビューして、評価して、直すべき点を挙げて | 評価だけする（直さない） | `references/refine/review.md` |

- 動きの追加や調整（「動きを付けて」「動きがうるさい」）は、目的を「仕上げる」とし、`references/motion-web.md` もあわせて読む。動きを減らす依頼は「落ち着かせる」とする。
- 文章の直し（「見出しのコピーを考えて」）は、`references/copy.md` に従う。この資料の4節の手順2〜5は同じく行う。

決まりごと：

- 目的は1つに絞る。2つに当たる依頼（「見やすくして、少し落ち着かせて」）は、両方の手順書を読み、表の上にあるほうから順に行う。3つ以上に当たる依頼と、どれにも当たらない依頼は「仕上げる」として扱う。
- 依頼の言葉が曖昧でも、目的を聞き返さずに振り分ける。直す範囲（どの画面か）が分からない場合だけ、1回聞く。サブエージェントとして動いているなど答える人がいない場合は、依頼に名前の出た画面か、最もよく使う画面を対象にする。
- 振り分けた目的と対象を、作業の前に1行で宣言する。例：「『見やすくする』として、設定画面（`src/pages/Settings.tsx`）を直す」。

## 3. 守る範囲

直すのは、目的に関係する場所だけである。次のものは引き継ぐ。

- **見た目の系統**：色、書体、角丸、余白の段階、影などのトークンと、記憶のフック。値を変える場合は、個々のクラスではなくトークンの値を変える。トークンがない場合は、直す範囲で使う値だけを `references/tokens-tailwind.md` の名前で `@theme` にまとめ、報告に書く。頼まれていないのに、プロジェクト全体をトークンに作り替えない。プロジェクトのルートに `DESIGN.md` があれば、そこに書かれた系統も引き継ぐ（`../design-core/references/design-system.md` の1節）。
- **文章**：利用者の書いた文章は言い換えない。`../design-core/references/anti-patterns.md` の W4 に当たる説明を消すことはよいが、消したものはすべて報告に書く。数字や実績などの事実を足さない。
- **機能と操作の手順**：ボタンや項目を消さない。使う頻度が低いものを隠す（段階的に見せる）のはよいが、消したいものは報告で提案するだけにする。
- **技術スタック**：フレームワーク、CSS の書き方、部品のライブラリを変えず、新しい依存を足さない。React Aria Components や Iconify のないプロジェクトでは、今ある部品の作り方に合わせる。

禁止リスト（`../design-core/references/anti-patterns.md`）に当たるものは、目的と直接関係しなくても、対象の画面の中なら直してよい。対象の外の画面で見つけたものは直さず、報告に書く。

## 4. 進め方

1. **読み込み**：SKILL.md の手順1を行う（design-core とユーザーの調整欄）。
2. **今の画面を見る**：
   - 対象の画面を SKILL.md の 5.2 の方法で撮る（直す前）。直す前の画像は、直した後と比べるために残しておく。
   - SKILL.md の 5.1 の自動チェックを実行し、違反を控える。
   - 画面の種類（サイト系／アプリ系）を SKILL.md の手順2の問いで判定し、手順2の後の表にあるモードのファイルを読む。テーマは今の対応を引き継ぐ。
   - トークンを定義した CSS（`@theme` など）を読み、今の系統を把握する。
3. **問題を書き出す**：振り分けた手順書の「見る点」に沿って、直す前の画像から問題を3〜7個に絞る。1つにつき「場所：何が問題か（根拠の番号）」を1行で書き、効果の大きい順に並べる。根拠の番号は `../design-core/references/critique.md` の C 番号か、`../design-core/references/anti-patterns.md` の項目番号を使う。
4. **直す**：手順書の「直し方」に従い、3の順に直す。部品を作り替える場合は、その部品のレシピ（SKILL.md の手順4の表）を読む。
5. **検証する**：SKILL.md の手順5と同じく、自動チェック、スクリーンショット、自己批評（最大2周）を行う。コンセプトの宣言がない画面では、`../design-core/references/critique.md` の C1 と C2 を「直す前の画面の印象と記憶のフックを保っているか」と読み替える。あわせて、手順書の「確かめ方」を行う。
6. **報告する**：5節の書式で報告する。

「評価だけする」の場合は、`references/refine/review.md` に従い、4〜5を行わない。

## 5. 報告の書式

```
## 目的と対象
- 目的：見やすくする（依頼：「設定画面を見やすくして」）
- 対象：<画面の名前とファイル>
- 種類：サイト系／アプリ系　テーマ：<引き継いだ対応>

## 見つけた問題と直したこと
1. <場所>：<問題>（<C 番号や X 番号>）→ <直したこと>
2. …

## 変えなかったこと
- <引き継いだ系統、触らなかった範囲>
- 消した説明文やラベル：<文章>（なければ「なし」）

## 実施した検証
- 自動チェック：直す前 <n> 件 → 直した後 0 件。抑制コメント：なし／<ファイル:行 ルール名 理由>
- スクリーンショット：直す前と後を、<幅>・<テーマ>で撮影（撮れなかった場合はその理由と代わりの確認）
- 自己批評：<1 または 2> 周。手順書の確かめ方の結果

## 直しきれなかった点・対象の外で気づいた点
- （なければ「なし」）
```
