# 直感的な UI の原則

アプリ系と判定した画面の実装の段階で読む。サイト系でも、フォーム、メニュー、ダイアログなど操作の部品を作るときは、2節、4節、7節に従う。

大手 OS メーカーの公開 UI ガイドラインを読み、Web のアプリに効く原則を自分の言葉でまとめたものである。各原則には「Web での実装」を添えた。部品ごとの具体的な作り方は、web スキルの references/components/ にあるレシピに従う。見た目の数値は `references/mode-app.md` に従う。

「直感的」とは、説明を読まなくても、見た目と過去の経験から次に何が起きるかを予測でき、その予測が当たることである。この資料の7つの原則は、すべて「予測できる」と「予測が外れても困らない」のどちらかを支える。

## 1. 見れば操作が分かる（アフォーダンス）

### 1.1 押せるものは押せる見た目にし、押せないものは押せる見た目にしない

- ボタンは面か枠を持ち、リンクは本文と区別できる色か下線を持つ。押せない要素（ただのカード、見出し、ラベル）には、ホバーで色が変わる、影が付くなどの反応を付けない。反応があると押せると思われ、押しても何も起きないと信用を失う。
- **Web での実装**：`cursor: pointer` とホバーの見た目は、操作できる要素にだけ付ける。行全体が押せる一覧では、行全体に反応を付け、押せる範囲と反応の範囲を一致させる。

### 1.2 利用者が知っている形と動きを使う

- 利用者はほかのアプリや現実の道具から学んだことを持ち込む。閉じる、検索、設定、共有などのよく知られた操作には、よく知られたアイコンと位置を使う。新しい操作方法（独自のジェスチャーなど）を作るのは、既存の方法で足りないときだけにする。
- スライダーは最小値を左（縦なら下）に置く。トグルは右側が ON である。こうした方向の約束を崩さない。
- **Web での実装**：アイコンは Iconify の定番のアイコンセットから選び、同じ意味には画面全体で同じアイコンを使う。独自のショートカットキーが OS やブラウザの定番（コピー、貼り付け、取り消しなど）と衝突しないようにする。

### 1.3 ラベルで結果を予測させる

- ボタンとメニューの項目は、押した結果を表す動詞で書く（「保存」「3件を削除」「招待を送る」）。「OK」「はい」「実行」のような、何が起きるか分からない言葉を避ける。
- 選択欄は、開かなくても中身が予想できるよう、現在の値かラベルを表示する。
- 押した後に追加の入力が必要な項目（別の画面やダイアログが開くもの）は、ラベルの末尾に「…」を付けて区別する（「名前を変更…」）。
- **Web での実装**：アイコンだけのボタンには、`aria-label` とツールチップの両方で同じ動詞のラベルを付ける。

### 1.4 操作の部品と中身を見た目で分ける

- 利用者の作ったもの・読むもの（中身）と、それを操作する部品は、面の色、書体の太さ、位置のどれかで分ける。両者が同じ見た目だと、どこを押せばよいか探すことになる。
- **Web での実装**：中身が色を多く持つ画面（写真、グラフ、キャンバス）では、操作の部品をグレーの段階だけで作り、アクセントは選択中の表示に限る（`../design-core/references/color.md` の1節）。

## 2. 状態を常に伝える（フィードバック）

### 2.1 押した瞬間に反応する

- 押したのに見た目が何も変わらないと、利用者は押せたのか分からず、もう一度押す。自前で作るボタンには、必ず押下中の見た目を付ける。
- **Web での実装**：`:active`（React Aria Components では `data-pressed`）で、面の明度を1段変えるか、わずかに縮める。処理を待たずに、押した時点で反応させる。

### 2.2 情報の重さに合わせて伝え方の強さを変える

| 情報の重さ | 伝え方 | 例 |
|---|---|---|
| 時々確かめればよい | 対象のそばに控えめに常に表示する | 件数、最終更新の時刻、同期中の印、保存済みの印 |
| 知っておくべきだが、今の作業は止めなくてよい | 画面の決まった場所に一時的に表示する | 完了の通知、元に戻す操作付きのトースト |
| 今すぐ判断しないと困る | 作業を止めて確認する | 予期しない、戻せないデータの消失 |

- 作業を止める伝え方（ダイアログ）を、重くない情報に使わない。多用すると、利用者は読まずに閉じるようになり、本当に重要なときに効かなくなる。情報を伝えるだけで、利用者が取れる行動がないなら、ダイアログにしない。
- 起動した直後にダイアログを出さない。お知らせは画面の中の決まった場所に置き、閉じるボタンとその場でできる操作を組にする。
- **Web での実装**：状態の表示は対象の要素の中か隣に置き、`aria-live` で読み上げにも伝える。トーストの作り方は web スキルの toast.md に従う。

### 2.3 処理中であることと、どれくらいかかるかを伝える

- 何も表示せずに待たせると、利用者は壊れたと考える。仮の表示（スケルトン）を先に出し、中身が届いたものから置き換える。
- 終わるまでの量が分かる処理には、量の分かる進捗（バーや割合）を使う。分からない処理には不定の表示を使い、途中で量が分かった時点で量の分かる表示に切り替える。進捗は正確に、なるべく一定の速さで進める。最初だけ速く進んで最後に止まる表示は、利用者を不安にさせる。
- 進捗の表示は止めない。止まった表示は、処理が固まったように見える。処理が本当に止まった場合は、理由とできることを示す。
- 「読み込み中」のような曖昧な言葉より、何をしているかを具体的に書く（「3件のファイルを変換している」）。
- 中断しても困らない処理には、キャンセルを置く。中断すると進捗が失われる場合は、そのことを伝える。
- 待っている間も、ほかの操作はできるようにする。
- **Web での実装**：0.3秒未満の処理では何も表示しない。それより長い処理の作り方は web スキルの loading.md に従う。進捗の表示は画面ごとに決まった場所に置く。

### 2.4 成功は重要なものだけ知らせ、失敗は必ず理由とともに知らせる

- 利用者は操作が成功する前提で使っている。すべての成功を知らせると騒がしい。支払い、送信、公開など重要な操作の完了だけを確認として示す。
- 実行できなかったときは、何が起きたか、なぜか、次に何をすればよいかを示す。「エラーが発生しました」だけで終わらせない。
- 実行できない操作（条件が揃っていないボタンなど）は、隠さずに無効の見た目で表示し、なぜ使えないかをツールチップか補足の文字で示す。
- **Web での実装**：エラーの文章は、原因の場所（入力欄の下、行の中）に置き、選択してコピーできるまま残す（`references/mode-app.md` の10節）。

### 2.5 色だけで伝えない

- 状態を色だけで示すと、色を見分けにくい人や、画面を見ていない人に伝わらない。色に加えて、アイコン、文字、形の変化のどれかを組み合わせる。
- **Web での実装**：エラーの入力欄は、枠の色に加えて、アイコンとエラーの文章を出し、`aria-invalid` と `aria-describedby` でつなぐ。

## 3. 一貫性

### 3.1 同じ見た目は同じ振る舞い、同じ振る舞いは同じ見た目

- 一度決めた部品の見た目と動きは、アプリ全体で変えない。利用者は1か所で覚えたことを別の場所でも使えると期待し、それが当たるほど早く慣れる。
- 同じものには同じ言葉を使う。「削除」と「消去」、「プロジェクト」と「作品」のように、同じ意味の言葉を混ぜない。
- **Web での実装**：部品はトークンと共通の部品から作り、画面ごとに見た目を作り直さない。ボタンの種類（主要、副次、危険）は3種類までにし、web スキルの button.md の区別に従う。

### 3.2 位置を保つ

- 同じ役割の操作は、どの画面でも同じ位置に置く（保存は右上、閉じるは右上の角など）。画面を移っても、利用者の手と目が覚えた位置を壊さない。
- 読み込みや状態の変化で、部品の位置が動かないようにする。押そうとした瞬間にボタンがずれると誤操作になる。
- **Web での実装**：遅れて届く中身の場所は、スケルトンで大きさを先に確保する。画面の遷移では、共通のヘッダーやサイドバーを動かさず、変わる部分だけを動かす。

### 3.3 プラットフォームの約束に従う

- Esc で閉じる、Enter で確定する、Tab で順に移る、取り消しとやり直しのショートカットキーなど、利用者が OS とブラウザで覚えた操作を、そのまま使えるようにする。
- **Web での実装**：React Aria Components の部品が持つキーボード操作を消さない。独自の部品を作る場合も、同じ操作に応えるようにする。

## 4. 取り消せる操作と確認の使い分け

### 4.1 確認するか、取り消せるようにするか

| 操作の性質 | 扱い |
|---|---|
| よくある操作で、取り消せる（メッセージの削除、項目の移動など） | 確認しない。実行したうえで、元に戻す操作を付けたトーストを出す |
| 利用者が意図してデータを捨てる操作（ゴミ箱を空にするなど） | 確認は1回だけにし、操作の名前をそのままボタンにする |
| まれな操作で、取り消せず、予期しないデータの消失が起きる | 実行の前に確認する |

- 確認のダイアログは、取り消しの代わりにならない。確認を毎回出すと、利用者は読まずに承認するようになる。取り消せるようにできる操作は、取り消せるようにするほうを先に検討する。
- **Web での実装**：削除は、すぐに画面から消し、実際の削除はトーストが消えるまで遅らせる方法が使える。トーストの表示時間は web スキルの toast.md に従う。

### 4.2 確認のダイアログの書き方

- 題名で、何が起きるかを具体的に書く（対象の名前、件数、戻せないこと）。「よろしいですか？」だけの題名にしない。
- ボタンは、結果を表す動詞にする（「3件を削除」「キャンセル」）。「OK」「はい」「いいえ」にしない。
- 戻せない操作のボタンは、危険な操作の見た目（エラー（危険）の色。`../design-core/references/color.md` の1節と調整欄の状態の色）にする。予期しない消失を確認する場合は、そのボタンを Enter で即実行される既定のボタンにしない。4.1 の表の2行目のように、利用者が意図して選んだ操作を確認する場合に限り、既定のボタンにしてよい。
- 取り消す手段は、キャンセルのボタンに加えて、Esc と背景のクリックでも使えるようにする。ただし、戻せない操作の確認のダイアログは背景のクリックでは閉じない（Esc とキャンセルで閉じる）。確認の途中で背景に触れただけで閉じると、確認したかどうかが分からなくなるためである。
- **Web での実装**：React Aria Components の `Dialog` に `role="alertdialog"` を指定して使う。予期しない消失を確認する場合は、最初のフォーカスをキャンセルのボタンに置く。作り方は web スキルの modal.md に従う。

### 4.3 取り消しの結果を予測でき、見えるようにする

- 何が取り消されるかを言葉で示す（「『見出し』の変更を取り消す」）。利用者は直前に何をしたかを覚えていないことが多い。
- 取り消した結果が画面の外にある場合は、そこまで移動して、変わった場所を一時的に強調する。何も変わらないように見えると、利用者は取り消しを繰り返す。
- 取り消しの回数を不必要に制限しない。スライダーのドラッグのような連続した細かい変化は、1回の取り消しにまとめる。
- **Web での実装**：取り消しの履歴は操作の単位で積み、ドラッグは `onChangeEnd` の時点で1件として記録する。

### 4.4 入力を失わせない

- 入力の途中でダイアログやパネルを閉じようとしたときは、失われる内容を示して確認する。入力のない状態なら、確認せずに閉じる。
- エラーが起きても、入力した内容を消さない。
- **Web での実装**：フォームの「変更あり」の状態を持ち、閉じる操作とページの離脱（`beforeunload`）で確認する。

## 5. 迷わせない導線（1画面1つの主目的）

### 5.1 1画面に主目的を1つ

- 画面ごとに「この画面で最もしてほしいこと」を1つ決め、主要な操作の見た目をそれだけに使う。
- 優先度の差は、ボタンの大きさではなく見た目の種類（反転した面、枠だけ、文字だけ）で示す。同じ大きさのボタンは同列の選択肢に見え、大きさだけが違うボタンは意図が読みにくい。
- 戻せない破壊的な操作を、主要な操作の見た目にしない。目立つボタンは、読まずに押されることがある。
- **Web での実装**：反転した面（`../design-core/references/color.md` の2節）は1つの領域に1つまでにする。主要なボタンは、フォームやダイアログでは右下、ツールバーでは右端に置き、画面全体で揃える。

### 5.2 重要なものを読み始めの位置に置く

- 利用者は左上から読み始める。最も重要な情報と操作を、左上から主要な視線の流れの上に置く。
- 関係する要素は揃えて近くに置き、関係の薄いものは余白か区切りで離す。
- **Web での実装**：余白の段階は `references/mode-app.md` の3.3節に従い、まとまり同士の間隔をまとまりの中の2倍以上にする。

### 5.3 モーダルは必要なときだけ、短く

- モーダル（ダイアログや全画面の編集）は、利用者を元の作業から切り離す。集中が必要な短い作業か、重要な判断のときだけ使う。
- モーダルの中で画面の階層を作らない。モーダルを重ねて開かない。閉じ方を必ず見える形で用意し、題名でモーダルの目的を示す。
- **Web での実装**：モーダルを開く前に、その場で編集する、横にパネルを開く、ポップオーバーで済ませる方法を検討する。

### 5.4 すぐに使い始められるようにする

- 最初の設定や説明を必須にしない。妥当な既定値を用意し、利用者がすぐに本来の作業を始められるようにする。
- 使い方は、まとめて説明するより、使う場面でヒントとして示す。説明の流れを作る場合は、短くし、飛ばせるようにする。
- 空の画面（データがまだない状態）は、次にすべき操作を1つ示す場所として使う。
- **Web での実装**：空状態の作り方は web スキルの states.md に従う。空状態は、アプリ系の記憶のフックを置く場所の候補でもある（`references/mode-app.md` の1節）。

## 6. 段階的に見せる

### 6.1 よく使うものは常に、高度なものは開いたときだけ

- 選択肢が多すぎる画面は、必要なものを探す時間を増やす。よく使う操作は常に見せ、高度な設定やまれな操作は折りたたむ。
- 折りたたむ部分には、中に何があるかが分かるラベルを付け（「詳細設定」「書き出しの設定」）、開閉の印をその内容の近くに置く。1つの領域に開閉の部品を何個も置かない。
- **Web での実装**：React Aria Components の `Disclosure` を使い、開閉の印は Iconify のアイコンを回転させて示す。開閉の動きは `references/mode-app.md` の11節の値を使う。

### 6.2 行ごとの操作は必要になったときに見せる

- 情報の多い一覧では、行ごとの操作をホバー時やフォーカス時だけ見せ、読んでいる間は隠す。作り方は `references/mode-app.md` の8節に従う。
- **Web での実装**：行に `group` を付け、操作の部品を `opacity-0 group-hover:opacity-100 group-focus-within:opacity-100` で切り替える。`@media (hover: none)` では常に表示する。

### 6.3 メニューの組み立て

- よく使う項目を上に置き、関係する項目を区切り線でグループにする。関係する項目は、使う頻度に差があっても同じグループに入れる。
- 使えない項目は隠さず、無効の見た目で表示する。メニューの構造が変わらないため、利用者は場所を覚えられる。
- サブメニューは1段までにし、項目は5個程度までにする。項目が多すぎるメニューは、別のメニューに分ける。
- 同じグループの項目は、アイコンをすべてに付けるか、どれにも付けないかのどちらかにする。
- 項目のショートカットキーは右端に表示する（`references/mode-app.md` の7節）。
- **Web での実装**：React Aria Components の `Menu` と `MenuSection`、`Separator` を使う。長い選択肢の一覧には検索欄を付ける（web スキルの select.md）。

## 7. 誤操作を防ぐ

### 7.1 危険な操作を、よく使う操作から離す

- 削除などの戻せない操作は、よく使う操作の隣に置かない。「その他」メニューの中や、区切り線の後ろの最後に置く。
- 危険な操作は、危険な操作の見た目で区別する。ただし画面の中で最も目立つ見た目にはしない。
- **Web での実装**：危険な操作のボタンは、エラー（危険）の色（トークン --color-danger。`../design-core/references/color.md` の調整欄の状態の色）を、通常時は文字か枠にだけ使い、面を塗るのは確認のダイアログの中だけにする。

### 7.2 入れられる値を部品で制限する

- 自由に入力させて後からエラーを出すより、最初から正しい値しか入らない部品を使う。決まった選択肢なら選択欄、範囲のある数値なら最小値と最大値を持つ数値入力、日付なら日付の部品を使う。
- 数値入力は、マウスのホイールで意図せず値が変わらないようにする（`../design-core/references/anti-patterns.md` の X16）。
- **Web での実装**：React Aria Components の `NumberField` に `minValue`、`maxValue`、`step`、`formatOptions` を指定する。作り方は web スキルの number-field.md に従う。

### 7.3 入力欄のラベルと検証

- プレースホルダーをラベルの代わりにしない。入力を始めると消え、何を入れる欄だったか分からなくなる。ラベルは入力欄の外に常に表示する。
- 入力欄の幅は、入る文字の量に合わせる。郵便番号の欄を全幅にしない。
- 検証は、入力の途中では行わず、欄を離れたときか送信のときに行う。送信で失敗したら、最初のエラーの欄にフォーカスを移す。
- Tab での移動の順番を、見た目の順番と一致させる。
- **Web での実装**：React Aria Components の `TextField` の `validationBehavior="aria"` とエラーの文章を使う。作り方は web スキルの text-input.md に従う。

### 7.4 二重の実行と押し間違いを防ぐ

- 送信や支払いのボタンは、処理中は読み込み中の状態にし、もう一度押せないようにする。押したことが見た目で分かるため、利用者も押し直さない。
- 押せる範囲を十分に取り、隣の部品との間に余白を置く。数値は `references/mode-app.md` の調整欄に従う。
- **Web での実装**：ボタンの `isPending` の状態を使い、処理中もボタンの幅を変えない（ラベルを残したまま、横に進捗の印を出す）。

## 実装の後の確かめ方

スクリーンショットと実際の操作で、次の問いに答える。`../design-core/references/critique.md` の自己批評と同じ周回の中で行う。

1. 押せるものと押せないものが、見た目だけで区別できるか（1節）。
2. 押したすべての部品が、押した瞬間に見た目を変えるか（2.1）。
3. 0.3秒以上かかる処理で、何も表示されない時間がないか（2.3）。
4. ダイアログで知らせている情報のうち、画面の中の表示で済むものはないか（2.2）。
5. 確認なしで実行される戻せない操作、確認が付いている取り消せる操作はないか（4.1）。
6. 1つの画面で、主要な操作の見た目が2つ以上ないか（5.1）。
7. キーボードだけで、すべての操作ができるか（3.3）。
