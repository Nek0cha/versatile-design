# 評価だけする

「どこが悪い？」「レビューして」「評価して」「直すべき点を挙げて」のように、直す前に問題を知りたいという依頼で読む。**コードは変更しない。** 直すように頼まれた後で、該当する目的の手順書に従って直す。

## 進め方

1. SKILL.md の手順1を行う（design-core とユーザーの調整欄）。
2. 対象の画面を SKILL.md の 5.2 の方法で撮り、5.1 の自動チェックを実行する。画面の種類（サイト系／アプリ系）を判定し、そのモードのファイルを読む。
3. `../design-core/references/critique.md` の C1〜C13 に、撮った画像（C13 は状態を変えた前後の画像か、コード）で答える。コンセプトの宣言がない画面では、C1 と C2 を「この画面から誰に向けたどんな印象が読み取れるか」「何で記憶に残るか」に読み替える。
4. アプリ系の画面と、フォームやダイアログのある画面では、`references/intuitive-ui.md` の「実装の後の確かめ方」にも答える。
5. 見つけた問題を、下の重さで分け、重い順に並べる。

| 重さ | 内容 |
|---|---|
| 重い | 使えない、誤操作を招く、読めない（はみ出し、コントラスト不足、押そうとした瞬間にずれる部品、確認のない戻せない操作など） |
| 中 | 分かりにくい、探しにくい（主役が決まらない、まとまりが見えない、説明に頼っている、抜けている状態） |
| 軽い | 見た目の質（禁止リストの定番の型、揃えのずれ、細部の不揃い） |

## 報告の書式

```
## 総評
（1〜2文。この画面が今どう見えるか）

## 良い点
- <点>：<なぜ良いか>（最大3つ。なければ書かない）

## 問題点
### 重い
1. <場所>：<何が問題か>（<C 番号や X 番号>）
   - 直し方の案：<1文>
   - 直すときの目的：<見やすくする／落ち着かせる／…>
### 中
…
### 軽い
…

## 実施した確認
- 自動チェック：<n> 件（<ルール名ごとの件数>）
- スクリーンショット：<幅>・<テーマ>（撮れなかった場合はその理由）

## 最初に直すなら
- <問題の番号>：<理由を1文>
```

- 問題は、場所を画像で指させるように具体的に書く（「余白が狭い」ではなく「設定の各まとまりの間が 16px で、まとまりの中と同じ」）。
- 良い点は理由を添える。良い点がなければ無理に書かない。
- 点数は付けない。
